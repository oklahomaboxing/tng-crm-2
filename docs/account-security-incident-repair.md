# Account security repair — October 26, 2026

Access tokens are now bound to the current account password hash, role, and revocation generation through a keyed digest. The digest contains no reusable password hash. Both CRM/academy and the separate Clover token audience check it. Password changes and **Sign out all devices** reject existing tokens immediately. Tokens issued before this deployment lack the binding and are rejected, requiring a one-time sign-in for every account. Customer admission QR codes and ticket access tokens use their existing separate verification and are unaffected.

Administrators can open **Security Center**, enter their current password, and select **Set up authenticator**. Scan the QR locally in an authenticator app, enter a code to confirm, and privately save the ten one-use recovery codes. Enrollment revokes prior sessions. Subsequent logins require an authenticator or recovery code. Secrets are encrypted at rest; recovery codes are stored as keyed hashes. Codes cannot be replayed, failures use account lockout, setup expires after ten minutes, and password resets preserve MFA. Enrollment requires the account owner and is not automatically completed by deployment. The existing Clover APK has no authenticator field: use a separate staff account for POS until its UI is upgraded; the backend does not bypass MFA for POS.

Security Center no longer presents a hard-coded 95% assessment. Password resets and session revocations generate security events, and authentication responses are marked no-store. Admin password resets use the same twelve-character complexity policy as email resets.

The Resend incident requires rotating the production key to domain-restricted sending access, confirming it is deployed, then revoking previous full-access keys. Provider account sessions, login passwords, MFA, and unknown team members must also be reviewed by the account owner in Resend, DigitalOcean, GitHub, and the recovery email account. API key rotation does not expel a person who still controls a provider dashboard. Preserve provider audit records and investigate unauthorized activity; these repairs do not establish the original entry point or prove that no data was accessed.

Validation uses isolated test databases: password reset invalidates CRM, academy, and Clover sessions; legacy tokens fail; revocation requires current credentials; authenticator enrollment, verification, replay rejection, lockout, and one-time recovery work; email reset preserves MFA. Existing stabilization, Clover, and ticketing regressions and the frontend build are run before deployment.
