# Member profiles and Clover reconciliation

Admin → Members now includes **Add Member** and **Sync Clover Customers**. The directory includes customer profiles and pending/manual members, including people with no paid membership sale. Portal status distinguishes active, disabled, activation sent, access not sent and missing email. The paid-membership dashboard retains its paid-sale filter.

Creating a profile assigns missing card credentials and a short numeric member-number alias. It does not create a sale, mark a waiver signed, grant active gym access, or set a password. Admins may optionally send an activation email; a failed email leaves the created profile available for retry from its profile page. Existing card and QR values remain unchanged. A customer must set their own password through the existing expiring activation flow.

Clover reconciliation reads `/v3/merchants/{merchant}/customers` with **CLOVER_API_TOKEN**, not the Hosted Checkout private key, and paginates with limit/offset. All pages must load before applying changes. Profiles match on Clover customer ID first, then unambiguous normalized email or phone; names alone never merge people. Conflicting/shared contacts and existing conflicting Clover links are reported by customer ID for duplicate review. Populated CRM contact details, login ownership, membership dates, sales and consent are preserved.

The background worker runs on startup and every ten minutes while Clover merchant/API credentials exist. `CLOVER_PROFILE_SYNC_ENABLED=0` disables it; `CLOVER_PROFILE_SYNC_INTERVAL_SECONDS` defaults to 600 (minimum 300). It creates/links profiles only, with no automatic marketing messages or activation-email backfill. Multiple workers serialize profile writes with a PostgreSQL transaction advisory lock shared by manual creation and paid imports. Provider errors contain status/actionable guidance, not provider bodies or credentials.

Paid Hosted Checkout retries now retry a failed activation email without recording another payment or extending the membership again. New paid POS membership imports send the same idempotent activation invitation after payment commits. Existing activated/disabled accounts and pending invitations are preserved. Legacy retail profiles with an `active` schema default do not qualify as active gym memberships.

Validation: isolated database tests cover manual creation/access controls, duplicate contacts, name-only customers, repeat imports, pagination failures, card collisions, preservation of paid memberships/QRs, failed email retries, new POS membership activation, and unpaid customer check-in rejection. Mock browser review verifies admin creation, sync feedback, directory status, staff controls and partial email failure without real messages.
